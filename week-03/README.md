# W3 — 연산자

**주제**: 산술 · 비교 · 논리 · 할당 연산자, 우선순위, 예측→검증 습관

## 학습목표

W2에서 값에 이름을 붙였으니, 이제 그 값들로 계산합니다. 연산자는 몇 개 안 되지만
**어느 것이 먼저 계산되는지**와 **타입이 다른 값을 만나면 어떻게 되는지**에서 갈립니다.

이번 주 과제는 네 단계입니다. **먼저 연산자를 하나씩 써보며 익히고**, 그 규칙으로
표현식의 결과를 **예측해 커밋한 다음**, 실행해서 **대조**합니다. 마지막으로 말로 된 규칙을
**직접 식으로 옮겨봅니다.**

예측은 찍기가 아닙니다. 앞 단계에서 알아낸 규칙을 적용해보는 것이고, 그래서 틀렸을 때
**내 규칙의 어디가 잘못됐는지** 짚을 수 있습니다. 맞히는 게 목적이 아니라 그걸 찾는 게 목적입니다.

- 산술 연산자로 계산하고, 우선순위에 따라 결과가 달라지는 것을 확인할 수 있다.
- 괄호로 계산 순서를 바꿀 수 있다.
- `/`와 `%`의 차이를 설명하고, 나머지 연산이 필요한 상황을 예로 들 수 있다.
- 비교 연산자의 결과가 불리언이라는 것을 확인하고, 그 값을 변수에 담아 쓸 수 있다.
- `&&` · `||` · `!`의 결과를 예측할 수 있다.
- `+`가 문자열을 만났을 때와 `-`가 문자열을 만났을 때가 왜 다른지 말할 수 있다.
- `+=` 같은 복합 할당이 무엇의 줄임인지 설명할 수 있다.
- **직접 실험해서 알아낸 규칙으로** 처음 보는 표현식의 결과를 예측할 수 있다.
- 예측이 어긋났을 때, 내 규칙의 어느 부분이 잘못됐는지 짚어낼 수 있다.

> 한가지 주제가 90분 넘게 막히면 질문하세요. 30분쯤 막히면 `week-03/읽으면진다-3주차치트노트.md`를 보셔도 됩니다.
> 단, **1단계를 직접 해본 뒤에** 펴세요.

## 과제: 연산자 익히고, 예측하고, 검증하고, 써먹기

### 1단계 — 연산자 익히기

`week-03/playground.js`에서 여러 연산을 직접 출력하며 알아냅니다.
알아낸 것은 `week-03/notes.md`에 한 줄씩 적습니다.

- [ ] 산술 연산자 `+` `-` `*` `/` `%` `**`를 각각 실행해보기
  - 같은 두 수(예: `10`과 `3`)로 여섯 개를 전부 돌려 결과를 나란히 출력
  - `/`와 `%`가 각각 무엇을 돌려주는지 `notes.md`에 한 줄씩
  - `**`는 두 수를 바꿔서도 해보기 (`2 ** 3`과 `3 ** 2`)
- [ ] 계산 순서 확인하기
  - `3 + 4 * 2`와 `(3 + 4) * 2`를 출력해 비교
  - 괄호가 없을 때 무엇이 먼저 계산되는지 `notes.md`에 한 줄
- [ ] 비교 연산자 `>` `>=` `<` `<=` `===` `!==` 써보기
  - 결과를 `typeof`와 함께 출력
  - 비교의 결과가 어떤 타입인지 `notes.md`에 한 줄
- [ ] 논리 연산자 `&&` `||` `!` 써보기
  - `true`와 `false`를 조합해 네 경우를 전부 확인
  - `!0`, `!''`처럼 불리언이 아닌 값에도 `!`를 붙여보고 결과 기록
- [ ] 복합 할당 `+=` `-=` `*=` 써보기
  - `+=`가 무엇의 줄임인지 `notes.md`에 한 줄
- [ ] 타입이 다른 값을 섞어보기
  - `'5' + 2`와 `'5' - 2`를 출력
  - W2에서 배운 **암묵적 변환**이 여기서 어떻게 일어나는지 `notes.md`에 한 줄

### 2단계 — 예측하고 커밋하기

- [ ] `week-03/predictions.md`의 표현식 10개를 예측해 적고 **커밋**
  - 근거란에 **1단계에서 알아낸 규칙**을 쓸 것. "느낌상"은 근거가 아닙니다
  - 1단계에서 다루지 않은 것이 하나 있습니다. 모르겠으면 `모름`이라고 쓰고, 왜 모르겠는지 적으세요
  - `check.js`는 아직 열지 마세요
  - 이 파일만 담아 커밋 (`git add week-03/predictions.md`)

### 3단계 — 검증하고 별도 커밋하기

- [ ] `node week-03/check.js`로 실행해 결과 대조
  - 결과를 `notes.md` 표에 옮기고 일치 여부 표시
  - 틀린 항목은 **내가 세운 규칙의 어디가 잘못됐는지**를 한 문단씩 (MDN 링크 첨부)
  - 예측 커밋과 별도로 커밋

### 4단계 — 규칙을 식으로 옮기기

말로 된 규칙을 연산자로 번역합니다. `week-03/leap-year.js`를 만드세요.

**윤년 규칙**
1. 4로 나누어떨어지면 윤년이다
2. 단, 100으로 나누어떨어지면 윤년이 아니다
3. 단, 400으로 나누어떨어지면 윤년이다

- [ ] 연도를 변수에 담고, 윤년인지 아닌지를 **불리언 값**으로 판정해 출력하기
- [ ] 판정 결과만 찍지 말고, **규칙 세 개가 각각 참인지 거짓인지도 함께 출력**하기
  - 이런 줄이 나와야 합니다

    ```
    2000년 → 4의 배수: true / 100의 배수 아님: false / 400의 배수: true / 윤년: true
    1900년 → 4의 배수: true / 100의 배수 아님: false / 400의 배수: false / 윤년: false
    ```

- [ ] 여섯 해를 넣어 돌리고, **출력된 결과를 그대로** `notes.md` 표에 옮기기
  - 2024 / 2023 / 1900 / 2000 / 2100 / 2400
  - 손으로 채우지 마세요. 코드가 찍어낸 것을 옮기는 겁니다
  - 표를 보고 **1900년과 2000년이 어느 칸에서 갈리는지** 한 줄로 적기

- [ ] 식에서 **괄호를 빼보고** 여섯 해를 다시 돌려보기
  - 결과가 하나도 안 바뀝니다. **왜 안 바뀌는지** `notes.md`에 설명
  - `&&`와 `||` 중 무엇이 먼저 계산되는지가 답입니다
  - 그런데도 괄호를 남겨두는 편이 나은 이유를 한 줄 더

### 제약

- 1단계를 건너뛰고 예측부터 하지 말 것
  - 근거 없는 예측은 찍기입니다. 찍은 답은 틀려도 배울 게 없습니다
- 예측 커밋 없이 검증 결과만 올리면 반려
  - 예측이 없으면 무엇을 잘못 알고 있었는지 확인할 방법이 없습니다
- 10개를 한 번에 실행해놓고 예측란을 채우지 말 것
  - 결과를 먼저 보면 "알고 있었던 것 같은" 착각이 생깁니다
- 계산 중간값도 변수에 담아 이름을 붙일 것. 한 줄에 몰아쓰기 금지
  - 4단계에도 그대로 적용됩니다. 같은 비교를 두 번 적고 있다면 이름을 붙일 때입니다
  - `(a * b - c) * d / 100`처럼 이어붙이면 틀렸을 때 어디가 틀렸는지 못 찾습니다
- 1단계는 검색하기 전에 먼저 실행해볼 것
  - 답을 먼저 읽으면 실험할 이유가 사라집니다. 검색은 확인용으로 마지막에
- 4단계에서 조건문(`if`) 사용 금지. 불리언 값만으로 해결할 것
  - 조건문은 다음 주 주제입니다. 비교와 논리 연산의 결과가 그 자체로 참/거짓 값이라는 걸 먼저 확인하세요
- `var` 금지, 의미 없는 변수 이름 금지 (W2와 같은 규칙)

### 완료 기준

- `notes.md`에 1단계에서 알아낸 것이 연산자별로 한 줄씩 정리되어 있음
- 예측 → 검증 커밋 2개가 순서대로 남아 있음 (`git log --oneline`으로 확인 가능)
- 예측의 근거란이 비어 있지 않음. `모름`이라고 적었다면 왜 모르겠는지가 함께 적혀 있음
- 표 10행이 전부 채워지고 일치 여부가 표시되어 있음
- 틀린 항목마다 **내 규칙의 어디가 잘못됐는지**가 적혀 있음
- `'5' + 2`와 `'5' - 2`의 결과가 왜 다른지 설명되어 있음
- 여섯 해의 윤년 판정이 전부 맞고, 규칙 세 개의 참·거짓까지 출력되어 표로 기록되어 있음
- 1900년과 2000년이 어느 칸에서 갈리는지 적혀 있음
- **마지막 판정 줄만 읽어도** 윤년 규칙 세 개가 무엇인지 읽힘
- 괄호를 빼도 결과가 같은 이유(`&&`와 `||`의 우선순위)가 적혀 있음
