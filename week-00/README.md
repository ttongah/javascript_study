# W0 — GIT과 저장소 세팅

**주제**: Git/GitHub, 커밋과 메시지, .gitignore

## 학습목표

이번 주 결과물은 캡처 몇 장이지만, 진짜 목표는 앞으로 26주 동안 매주 반복할 작업 흐름을
손에 익히는 데 있습니다. 과제를 마쳤을 때 아래를 할 수 있으면 됩니다.

- 내 PC의 저장소와 GitHub의 저장소가 별개임을 이해하고, `git pull`로 GitHub의 변경 사항을 내 PC로 가져올 수 있다.
- `origin`과 `main`이 각각 무엇을 가리키는 이름인지 설명할 수 있다.
- 브랜치가 폴더 복사본이 아니라 커밋을 가리키는 이름표임을 이해하고, 명령어로 브랜치를 만들어 체크아웃할 수 있다.
- `git add` 명령어의 의미를 알고, git이 추적하는 파일과 추적하지 않는 파일을 구분할 수 있다.
- `.gitignore`를 작성해, PC에 파일이 존재해도 git이 인식하지 않게 만들 수 있다.
- GitHub에 올려서는 안 되는 파일이 무엇이고 왜 그런지 스스로 판단할 수 있다.
- 커밋이 되돌릴 수 있는 최소 단위임을 이해하고, 하나의 작업을 목적 단위로 나누어 커밋할 수 있다.
- 커밋 메시지 컨벤션을 조사해 자신의 기준을 세우고, 그 기준대로 메시지를 작성할 수 있다.
- 로컬 커밋과 원격 반영이 다름을 이해하고, `git push`로 브랜치를 올린 뒤 PR을 생성할 수 있다.
- 명령어를 실행한 뒤 git의 응답을 읽고, 성공했는지 실패했는지 판단할 수 있다.

## 과제: 저장소 셋업과 커밋, pull과 push, .gitignore의 이해.

### 요구사항

- [ ] 과제 문서를 깃허브에서 pull 받기
  - 과제를 터미널을 이용해 pull 받기
  - 명령어 실행한 화면을 캡쳐하여 프로젝트에 첨부
- [ ] 명령어를 이용해 브렌치를 생성하기
  - 브렌치 이름은 `week-00`
  - `week-00` 브렌치를 생성하고 체크아웃하기
  - 브렌치 생성과 체크아웃한 명령어를 캡쳐해 프로젝트에 첨부
- [ ] `.gitignore` 파일의 작성과 이해
  - `.gitignore` 파일의 작성법을 익히기
  - github에 업로드 해서는 안 되는 파일을 조사(예시: ide 설정 폴더)
  - 예시 파일을 작성하여 파일이 존재함에도 git이 인식하지 못하는 것을 캡쳐하여 프로젝트에 첨부
- [ ] 위 과제를 각각 별도로 커밋하기
  - 올바른 커밋 메시지 작성법을 조사하기
  - 조사한 대로 메시지를 작성하여 `week-00`에 커밋
  - 커밋 명령어를 실행한 화면을 하나만 캡쳐하여 프로젝트에 첨부. (모든 과제가 아닌 하나만 해도 무방)
- [ ] 커밋한 내용을 깃허브에 push하고 pr하기
  - `week-00` 브렌치를 명령어로 push 하고, github 웹사이트에서 main 브렌치로 pr하기

### 제약

- 터미널에서 git 커멘드만을 사용
- github desktop, vs code 및 ide 내장 git 클라이언트 사용 금지.
  - GUI 버튼 하나가 여러 단계를 한꺼번에 실행합니다. `add`와 `commit`과 `push`가 각각 다른 일이라는 걸 모르면 "커밋은 했는데 GitHub에 안 보여요"에서 어디가 문제인지 짚지 못합니다
- **`git add .` 금지.** 파일 단위로 stage할 것 (`git add week-00/README.md`)
  - 파일을 하나씩 골라 담아봐야 스테이징이 커밋과 따로 있는 이유가 보입니다
- 캡처는 결과 화면까지 포함할 것
  - git이 뭐라고 대답했는지 읽지 않으면 실패해놓고 성공한 줄 알고 넘어갑니다

### 완료 기준

- pull, 브렌치 생성, 체크아웃, 커밋 명령어 캡쳐가 있음.
- .gitignore 파일이 존재하며, 명시된 파일이 커밋되지 않고, 해당 파일이 pc에 존재하는 캡쳐가 있음
- 커밋이 개별적으로 구성되며, 커밋 메시지가 읽기 쉽고 대중적임.
- 모든 과제가 github `week-00` 브렌치에 올바르게 푸시되며 main 브렌치에 pr이 됨
